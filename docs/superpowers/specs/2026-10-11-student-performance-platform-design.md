# Student, Class, Assessment Delivery & Adaptive Performance — Design

Date: 2026-10-11
Status: Approved (brainstorming), pending implementation plan

## Context

Claxi already has an authoring domain (subjects, grades, topics, BNCC
catalog, questions, question_alternatives, assessments,
assessment_questions), an AI-generation/credits domain
(ai_generation_operations, credit_accounts, credit_transactions), and
multi-tenant auth tables managed by Better Auth (organization, user,
member, session, invitation, refresh_token, verification, account).

That covers a teacher authoring questions and assessments and exporting
them to PDF. It does not cover:

- Registering students (independent or grouped into classes).
- Letting students answer assessments inside the platform (via a public
  link, not just PDF export).
- Tracking student performance/growth over time.
- Feeding that performance data into AI-driven adaptive question
  generation and analysis.

This document specifies the schema additions needed to close that gap.
All new tables follow the existing conventions: snake_case unquoted
identifiers (except `"user"`, a reserved word), one entity per file in
`database/`, `UUID` primary keys generated by the application, lookup
tables with `id TEXT PRIMARY KEY` + `description TEXT NOT NULL` for
closed enumerations (seeded via `INSERT ... ON CONFLICT (id) DO
NOTHING` in the same file), and plain `FOREIGN KEY (...) REFERENCES
...` clauses (no named FK constraints) placed after the column list.

## Decisions carried from brainstorming

- A student record is **not** a Better Auth account. There is no
  login/password/email. A student is a record owned by one
  organization (like every other domain table); the same real person
  enrolled in two schools gets two independent, unrelated student
  records.
- A student may belong to any number of classes at the same time
  (many-to-many), or to none.
- Public assessment access is always authorized through a single
  auxiliary table (`assessment_access`) keyed by `(assessment_id,
  student_id)`. Releasing access "by class" is a backend business rule
  that expands into one row per enrolled student — the schema itself
  has no separate "class access" concept, keeping authorization logic
  in one place.
- A student authenticates to a public assessment link by typing one of
  three possible personal codes and telling the backend which kind it
  is: a system-generated internal enrollment number (always present), a
  CPF, or an external (school-issued) enrollment code (both optional).
- Public links need an availability window (open/close timestamps) and
  an optional per-attempt time limit.
- Multiple attempts per assessment are allowed, capped by a
  configurable `max_attempts` per assessment (NULL = unlimited).
- Objective questions (`MULTIPLE_CHOICE`, `TRUE_FALSE`) are graded
  automatically. Open-ended questions get a hybrid flow: AI suggests a
  score/feedback, a teacher can review and override it. Any answer,
  regardless of question type, may carry one or more image attachments
  (e.g., a photo of handwritten math work).
- Performance analysis needs real growth-over-time tracking, not just a
  single mutable aggregate. The design keeps raw submission/answer data
  forever and additionally writes periodic, immutable snapshots.
- Snapshots are kept at two granularities: BNCC skill (precise, feeds
  the adaptive AI) and topic (broader, for general reporting — also
  covers questions that were never tagged with a BNCC skill).
- Adaptive AI generation reuses the existing
  `ai_generation_operations` table rather than introducing a parallel
  tracking table; it gains a nullable `student_id` and two new
  `operation_type` values. Which skills drove a given generation stays
  in the existing `metadata` JSONB column — it is contextual, not
  something queried relationally.

## Schema additions

### 1. Students and classes

**`students`**
| column | type | notes |
|---|---|---|
| id | UUID PK | |
| organization_id | UUID NOT NULL | FK `organization` ON DELETE CASCADE |
| name | TEXT NOT NULL | |
| internal_enrollment_number | TEXT NOT NULL | system-generated at creation |
| cpf | TEXT NULL | |
| external_enrollment_code | TEXT NULL | |
| created_at, updated_at | TIMESTAMPTZ NOT NULL | |

Constraints: `UNIQUE (organization_id, internal_enrollment_number)`;
`UNIQUE (organization_id, cpf)` as a partial unique index `WHERE cpf IS
NOT NULL`; `UNIQUE (organization_id, external_enrollment_code)` as a
partial unique index `WHERE external_enrollment_code IS NOT NULL`.

**`classes`**
| column | type | notes |
|---|---|---|
| id | UUID PK | |
| organization_id | UUID NOT NULL | FK `organization` ON DELETE CASCADE |
| grade_id | UUID NULL | FK `grades` ON DELETE RESTRICT — optional link to the catalog grade/year |
| name | TEXT NOT NULL | e.g. "9º Ano A - 2026" |
| created_at, updated_at | TIMESTAMPTZ NOT NULL | |

Constraint: `UNIQUE (organization_id, name)`.

**`class_enrollments`** (many-to-many join, same shape as
`question_bncc_skills`: composite PK, no surrogate `id`)
| column | type | notes |
|---|---|---|
| class_id | UUID NOT NULL | FK `classes` ON DELETE CASCADE |
| student_id | UUID NOT NULL | FK `students` ON DELETE CASCADE |
| created_at | TIMESTAMPTZ NOT NULL | |

`PRIMARY KEY (class_id, student_id)`.

### 2. Public access and release

New columns on the existing `assessments` table (no new table — there
is one link configuration per assessment, not a history of links):

| column | type | notes |
|---|---|---|
| public_access_code | TEXT NULL UNIQUE | generated when sharing is enabled |
| public_access_enabled | BOOLEAN NOT NULL DEFAULT FALSE | |
| opens_at | TIMESTAMPTZ NULL | |
| closes_at | TIMESTAMPTZ NULL | |
| time_limit_minutes | INTEGER NULL | per-attempt limit |
| max_attempts | INTEGER NULL | NULL = unlimited |

Checks: `closes_at IS NULL OR opens_at IS NULL OR closes_at > opens_at`;
`max_attempts IS NULL OR max_attempts >= 1`; `time_limit_minutes IS
NULL OR time_limit_minutes >= 1`.

**`assessment_access`** (single source of truth for "who can open this
assessment")
| column | type | notes |
|---|---|---|
| assessment_id | UUID NOT NULL | FK `assessments` ON DELETE CASCADE |
| student_id | UUID NOT NULL | FK `students` ON DELETE CASCADE |
| class_id | UUID NULL | FK `classes` ON DELETE SET NULL — traceability only, never part of the authorization check |
| granted_by | UUID NULL | FK `"user"` ON DELETE SET NULL |
| granted_at | TIMESTAMPTZ NOT NULL | |

`PRIMARY KEY (assessment_id, student_id)`.

Business rule (application layer, not DB): granting access "by class"
reads every `student_id` from `class_enrollments` for that class and
inserts one row per student with `class_id` set; granting "by student"
inserts a single row with `class_id` NULL. The only authorization
check anywhere in the backend is "does a row exist for this
`(assessment_id, student_id)`".

### 3. Submissions and answers

New lookup tables:
- `assessment_submission_statuses`: `IN_PROGRESS`, `SUBMITTED`,
  `GRADED`, `EXPIRED`.
- `student_answer_grading_statuses`: `AUTO_GRADED`, `PENDING_GRADING`,
  `AI_GRADED`, `TEACHER_GRADED`.
- New value added to the existing `file_purposes` lookup:
  `ANSWER_ATTACHMENT`.

**`assessment_submissions`** (one row per attempt)
| column | type | notes |
|---|---|---|
| id | UUID PK | |
| assessment_id | UUID NOT NULL | FK `assessments` ON DELETE CASCADE |
| student_id | UUID NOT NULL | FK `students` ON DELETE CASCADE |
| attempt_number | INTEGER NOT NULL | |
| status | TEXT NOT NULL DEFAULT 'IN_PROGRESS' | FK `assessment_submission_statuses` |
| started_at | TIMESTAMPTZ NOT NULL | |
| submitted_at | TIMESTAMPTZ NULL | |
| graded_at | TIMESTAMPTZ NULL | |
| total_score | NUMERIC(8,2) NULL | sum of awarded points, filled once grading completes |
| max_score | NUMERIC(8,2) NULL | sum of possible points, captured at submission time |
| created_at, updated_at | TIMESTAMPTZ NOT NULL | |

Constraints: `UNIQUE (assessment_id, student_id, attempt_number)`;
`CHECK (attempt_number >= 1)`.

**`student_answers`** (one row per question within a submission)
| column | type | notes |
|---|---|---|
| id | UUID PK | |
| submission_id | UUID NOT NULL | FK `assessment_submissions` ON DELETE CASCADE |
| assessment_question_id | UUID NOT NULL | FK `assessment_questions` ON DELETE RESTRICT |
| selected_alternative_id | UUID NULL | FK `question_alternatives` ON DELETE SET NULL |
| answer_text | TEXT NULL | |
| is_correct | BOOLEAN NULL | |
| score | NUMERIC(8,2) NULL | |
| grading_status | TEXT NOT NULL DEFAULT 'PENDING_GRADING' | FK `student_answer_grading_statuses` |
| ai_suggested_score | NUMERIC(8,2) NULL | |
| ai_feedback | TEXT NULL | |
| graded_by | UUID NULL | FK `"user"` ON DELETE SET NULL |
| graded_at | TIMESTAMPTZ NULL | |
| created_at, updated_at | TIMESTAMPTZ NOT NULL | |

Constraint: `UNIQUE (submission_id, assessment_question_id)`.

`grading_status` defaults to `PENDING_GRADING` only as the pre-insert
default. The application must grade objective answers
(`MULTIPLE_CHOICE`, `TRUE_FALSE`) synchronously on submission —
setting `is_correct`, `score`, and `grading_status = 'AUTO_GRADED'` in
the same write — so `PENDING_GRADING` in practice only applies to
`OPEN_ENDED` answers awaiting AI/teacher grading.

**`student_answer_attachments`**
| column | type | notes |
|---|---|---|
| id | UUID PK | |
| answer_id | UUID NOT NULL | FK `student_answers` ON DELETE CASCADE |
| file_id | UUID NOT NULL | FK `files` ON DELETE RESTRICT |
| created_at | TIMESTAMPTZ NOT NULL | |

Constraint: `UNIQUE (answer_id, file_id)`.

### 4. Performance snapshots

Both tables are append-only history (no `updated_at`); the cadence at
which snapshots are written (after every graded submission, nightly
batch, etc.) is an application concern, not a schema concern.

**`student_skill_performance_snapshots`**
| column | type | notes |
|---|---|---|
| id | UUID PK | |
| student_id | UUID NOT NULL | FK `students` ON DELETE CASCADE |
| skill_id | UUID NOT NULL | FK `bncc_skills` ON DELETE RESTRICT |
| snapshot_date | DATE NOT NULL | |
| correct_count | INTEGER NOT NULL DEFAULT 0 | |
| total_count | INTEGER NOT NULL DEFAULT 0 | |
| accuracy | NUMERIC(5,2) NULL | materialized `correct_count / total_count * 100` |
| created_at | TIMESTAMPTZ NOT NULL | |

Constraints: `UNIQUE (student_id, skill_id, snapshot_date)`; `CHECK
(correct_count >= 0 AND total_count >= correct_count)`.

**`student_topic_performance_snapshots`** — identical shape, `topic_id`
(FK `topics` ON DELETE RESTRICT) instead of `skill_id`. `UNIQUE
(student_id, topic_id, snapshot_date)`; same count check.

### 5. Adaptive AI integration

Extend `ai_generation_operations`:
- Add `student_id UUID NULL` → FK `students` ON DELETE SET NULL.

Add to the existing `ai_operation_types` lookup:
- `STUDENT_PERFORMANCE_ANALYSIS` — "Análise de desempenho do aluno"
- `ADAPTIVE_QUESTION_GENERATION` — "Geração adaptativa de questões"

Which skills/snapshots motivated a generation stays in the operation's
existing `metadata` JSONB column; no new relational table is
introduced for that, since it is contextual data that does not need to
be joined or indexed relationally today.

## Explicitly out of scope (YAGNI, revisit if needed)

- A generic polymorphic "performance dimension" table — rejected in
  favor of two concrete snapshot tables (skill, topic).
- A history table of multiple public-link generations per assessment —
  one link configuration lives directly on `assessments`.
- A relational table for AI target skills — kept in JSONB metadata.
- Any login/auth mechanism for students.
- Subject-level snapshots, time-spent-per-question, "skipped question"
  tracking — not requested.

## Cross-cutting notes for the implementation plan

- New domain tables follow the existing per-entity file convention in
  `database/` (e.g. `students.sql`, `classes.sql`,
  `class_enrollments.sql`, `assessment_access.sql`,
  `assessment_submissions.sql`, `student_answers.sql`,
  `student_answer_attachments.sql`,
  `student_skill_performance_snapshots.sql`,
  `student_topic_performance_snapshots.sql`), plus new lookup files
  (`assessment_submission_statuses.sql`,
  `student_answer_grading_statuses.sql`).
- Changes to existing files: `assessments.sql` (new columns + checks),
  `file_purposes.sql` (new seed row), `ai_generation_operations.sql`
  (new column), `ai_operation_types.sql` (new seed rows).
- Because `students`, `classes`, and everything downstream reference
  tables created earlier in this project (`organization`, `grades`,
  `assessments`, `bncc_skills`, `topics`, `files`, `"user"`), file
  creation/run order must respect those dependencies — consistent with
  the ordering constraint that already exists across the rest of
  `database/`.
